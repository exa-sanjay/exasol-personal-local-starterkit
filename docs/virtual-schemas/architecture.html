Virtual schemas: architecture

How exakit connect and exakit source make an external source readable from the local Exasol, for kit maintainers and developers. How to use it, source by source: Connecting external sources.

Code: setup/virtual-schemas/ Verified against commit 4ac1b91 Platform facts: Exasol Personal 2.3.0, Nano 2026.2.0-nano.3

1. Overview

A virtual schema VS_NAME is a schema in the local Exasol whose tables live somewhere else. Every query is translated by an adapter (a script inside the database) and sent to the source; nothing is copied. The kit's job is everything around that:

  • Download and verify the adapter, plus a JDBC driver where one is needed.
  • Install the runtime the adapter runs on (Java, a pinned Rust runtime, or the built-in Lua), asking before the one database restart.
  • Create the database objects: the CONNECTION holding the credentials, the adapter script, the virtual schema.
  • Prove the link by reading real rows, as the admin and as the read-only MCP user.
  • Keep it working afterwards: check, reauth, refresh, describe, remove.

It is a core kit feature, not a marketplace add-on. The engine is Python (stdlib plus pyexasol) and runs on the kit's pyexasol venv with python -I. Thin bash and PowerShell bridges call it. Each source type is a data folder (connector.json plus an optional hooks.py), so a new connector rarely needs engine code.

Three rules shape most of the design:
  1. A secret lives only in the database's CONNECTION object. It is never in the kit's files, logs or output.
  2. The kit drops only objects it tagged as its own (COMMENT managed by exakit virtual-schemas).
  3. New details replace working ones only after they are proven, through a staging connection.

The lakehouse route reads files directly from storage, without any compute at the source. The Databricks connector runs every query on a SQL warehouse.

7.1 First connect

lifecycle.connect through _apply. A failure anywhere in a first connect rolls back everything it made (_rollback).

sequenceDiagram
  autonumber

7.3 reauth: credentials replaced only once proven

sequenceDiagram
  autonumber
  actor U as User
  participant E as Engine
  participant D as Exasol
  participant S as Source
  U->>E: exakit source reauth sales --password-file new.pw
  E->>D: CREATE CONNECTION EXAKIT_SRC_SALES_NEW
  E->>D: probe through _NEW
  D->>S: login with the new password
  alt refused
    S-->>D: auth error
    E->>D: DROP CONNECTION _NEW
    E-->>U: refused (kind auth), old credentials untouched
  else accepted
    S-->>D: ok
    E->>D: CREATE OR REPLACE CONNECTION EXAKIT_SRC_SALES
    E->>D: DROP CONNECTION _NEW
    E-->>U: credentials replaced
  end

7.4 Lakehouse with vended credentials

The Unity Catalog route (catalog=unity, Delta log) and the Iceberg REST route (catalog=iceberg, Iceberg metadata) differ only in the catalog API and the metadata they follow.

sequenceDiagram
  autonumber
  participant X as Exasol
  participant A as LAKEHOUSE_ADAPTER (Rust)
  participant C as Catalog (Unity / Iceberg REST)
  participant S as Object storage (S3)
  X->>A: pushdown request for VS_NAME.T
  A->>C: load table (token from the CONNECTION)
  C-->>A: table location + metadata
  A->>C: temporary storage credentials
  C-->>A: short-lived S3 keys (no region: the kit supplies it)
  A-->>X: SELECT ... FROM LAKEHOUSE_SCAN(...) over the file list
  X->>A: LAKEHOUSE_SCAN, files spread by LAKEHOUSE_DISTRIBUTE_FILES
  A->>S: GET Parquet files (region, keys)
  S-->>A: data
  A-->>X: filtered rows

Databricks refuses step 4 for schemas on Default Storage, or without External data access and EXTERNAL USE SCHEMA (kind external_access). A Delta table whose newest commits live in Unity Catalog cannot be read on the Delta route (kind catalog_managed); the Iceberg REST endpoint reads it.

7.5 After every database start

sequenceDiagram
  autonumber
  actor U as User or login autostart
  participant K as exakit start database
  participant L as exasol launcher
  participant E as Engine (hook post-start)
  participant D as Database container
  U->>K: exakit start
  K->>L: start (creates a NEW container)
  L-->>K: running
  K->>E: hook post-start (only if a Java source exists)
  E->>D: link /etc/resolv.conf and /etc/hosts to /conf in the Java SLC
  E-->>K: ok, or skipped (never fails the start)

The official Java SLC image ships empty resolv.conf and hosts; without the links no host name resolves in a JDBC adapter. The Rust SLC links its own; Lua resolves names natively.

ConcernWhat to know
Connections start inside the databaseA source is reached from the database container, not from the host. localhost means the container itself; the kit rewrites a loopback host to host.containers.internal (except for the Exasol connector, whose source is this database).
Architectureruntime.db_arch picks the x86_64 or aarch64 asset for Rust runtimes and adapters. aarch64 (Apple silicon) is pinned but untested.
RestartsInstalling or replacing an SLC is the only step that restarts the database, and the kit asks first. Every start creates a new container, which is why the DNS links are reapplied (7.5).
TLSThe import process's Java trust store is empty, so JDBC sources are encrypted but not verified. Exasol is pinned by fingerprint. Rust adapters verify against their own CA bundle. Databricks metadata calls are pinned to the workspace certificate's SHA-256.
Windows networkingPorts published by Podman may answer on ::1 only; the engine's reachability check uses the host as given.

11. Keeping this page true

  • The diagrams are Mermaid source inside <pre class="mermaid"> blocks: edit the text and reload. Avoid semicolons in diagram text (Mermaid reads them as statement ends).
  • Update the page in the same commit as a change to the connect order, a new connector, a new runtime, or a new file or object name, and bump the commit in the header.
  • The user-facing behaviour is documented elsewhere: README.md, AGENTS.md, skills/exasol-virtual-schemas/SKILL.md, setup/help/virtual-schemas.json. This page explains how it works, not how to use it.
  • Diagrams render with Mermaid from a pinned CDN version; offline, the source text shows instead.
